# 원재료 상세 조회와 로컬 캐시 (앱22)

2026-10-15

## 뉴케어 표시 실패 원인

영양 DB의 제조사명(대상라이프사이언스)과 C002 원재료 DB의 업체명(대상웰라이프)이 달라 기존 companyVerified 검사가 원문 표시를 막았다. 이제 품목제조번호로 반환된 원문을 보여주고 업체명 차이를 경고한다. 이를 업체 동일성 확정이나 영양정보 자동 적용으로 사용하지 않는다. 알레르기/같은 시설 제조 정보는 미확인으로 유지한다.

## 저장/조회 변경

- 새 식사 기록의 nutrition_source에서 원재료 본문 ingredients를 제거한다. 제품 식별번호와 영양정보 출처는 유지한다. 기존 과거 DB 원재료 값은 자동 삭제하지 않았으며 상세 조회는 그 본문을 사용하지 않는다.
- 캘린더 식사 상세에서 각 음식의 원재료 정보 보기 버튼을 눌렀을 때만 조회한다.
- 품목번호가 있는 기록은 C002에 직접 조회한다. 번호가 없는 과거 기록은 공공 영양 후보를 조회하고 사용자가 제품/업체/규격을 확인한 뒤 원재료를 조회한다. 이름만으로 자동 연결하지 않는다.
- 식사 상세에 표시하는 값은 현재 조회/당일 캐시 정보이며 섭취 당시 원재료를 복원한 것이 아니다. 리뉴얼 가능성을 안내한다.

## 캐시 정책

휴대폰 앱 전용 로컬 저장소(SharedPreferences). 사용자ID+품목제조번호+현재 날짜로 구분한다. 같은 계정·제품은 당일 성공 응답을 재사용하고 다음 날 새로 조회한다. 앱 재시작 후에도 당일 캐시를 재사용한다. 동시에 눌러도 대기 중인 요청을 공유한다. 실패 응답은 저장하지 않아 사용자가 다시 시도할 수 있다.

조회 당시부터 7일 만료, 전체100건/2MiB 상한. 앱 시작·조회·저장 시 만료/초과 항목 정리. 앱이 실행되지 않는 동안 별도 백그라운드 삭제 작업은 하지 않으며 다음 실행 때 정리한다. 원재료 확인 화면과 식사 상세는 같은 캐시를 사용한다.

## 사진 저장과 용량

사진 바이트는 Supabase Storage의 meals 버킷에 서버 저장한다. 식사 DB에는 photo_path(경로)가 저장된다. 표시할 때 서버에서 다운로드하고 화면 메모리에 보관한다. 촬영/선택 과정에서는 휴대폰의 원본/임시 파일도 존재할 수 있으며 앱 기록용 원본 저장 장소는 서버다.

storage.objects 메타데이터 size 집계 실조회: 파일11개/1,373,278bytes(약1.31MiB), 평균124,843bytes(약122KiB). 프로젝트 meals 버킷 전체이며 특정 사용자의 용량으로 표현하지 않는다. Storage 메타데이터 집계라 기타 버킷·전송량·DB 용량은 포함하지 않는다. 현재 입력 사진은 사진 선택기의 max1600x1600, quality82 설정을 사용한다.
