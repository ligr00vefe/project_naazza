# 제품 앞면 인식 회귀 수정 (빌드 18)

사용자가 실패 원인 확인용으로 제공한 퀴노아 크래커와 뉴케어 당플랜 호두맛 사진을 동일한 Gemini 3.5 Flash-Lite로 검증했다. 사진 원본은 변경하거나 저장소에 복사하지 않았다.

## 원인
이전 프롬프트는 제품명·전체 중량·전체 영양성분표가 모두 읽힐 때만 foods를 반환하라고 요구했다. foodIdentity 역시 nutritionLabelReadable=true 및 모든 영양값을 필수로 검증했다. 제품 앞면 사진에서 제품명을 식별하더라도 영양표가 없으면 제품명까지 버리는 회귀였다. 숫자만 허용하는 영양정보 스키마는 미확인 값의 추정/0 채우기도 유발할 수 있었다.

원래 조건에서 두 실제 사진은 HTTP200, imageQuality=clear, failureReason=nutrition_unreadable, foods=[]였다. 각각 3.189초와 3.236초에 응답했으므로 이번 재현은 서버 무응답/시간 초과가 아니다.

## 수정
- 제품명 인식(identifiedProducts)과 완전한 영양정보(foods)를 분리한다.
- 이름과 맛/종류를 확실히 읽으면 영양표 없이도 제품명을 유지한다. 사진에서 읽힌 한 개 전체 용량/열량만 보존한다.
- 미확인 열량은 null, 미확인 용량은 빈 문자열이다. 읽지 못한 탄수화물/단백질/지방/나트륨을 0이나 기억하는 값으로 채우지 않는다. ml를 근거 없이 g으로 변환하지 않는다.
- 완전한 영양정보 검증은 유지하며, 숫자 스키마에는 null을 허용해 모델이 미확인 값을 비울 수 있도록 했다.
- 앱은 제품명이 확인되면 실패 대신 제품 카드와 확인된 정보를 표시한다. 기록 화면으로 제품명·확인된 용량/열량·사진을 넘기고 사용자가 검토한다.
- 용량이 미확인인 제품 기록의 기본값은 1개다. 열량이 비어 있으면 저장 시 null/열량 미기록으로 남기며 0kcal로 확정하지 않는다.
- 직접 입력·재촬영·사용자 재시도·분석 대기 종료 흐름을 유지한다. 임의 횟수 제한과 대기 차단은 없다.

## 실제 서버 검증
| 사진 | 전체 경과 | 결과 |
|---|---|---|
| 퀴노아 크래커 | 5.556초 | HTTP200, 제품명 유지, 열량 null, 완전 영양정보 후보 0 |
| 뉴케어 당플랜 호두맛 | 3.168초 | HTTP200, 한국어 제품명·200ml·200kcal 유지, 완전 영양정보 후보 0 |

둘 다 diagnosis=product_identified_nutrition_pending이다. 완전 영양정보를 수집했다는 의미가 아니라, 제품 식별 성공과 영양정보 보완 필요를 구분한다. 사진의 제품명·앞면 표시 정보만 검증했으며 제품 DB 검색이나 전체 영양성분의 확인으로 주장하지 않는다.

Flutter 테스트 18개와 정적 검사를 통과했다. Node에서는 제품명 보존, 미확인/기준 불명 열량 null 처리, 기존 완전 영양정보 검증 및 요청 시간 제한을 확인했다. 실제 서버 테스트 사진 삭제와 로그아웃도 확인했다.

## 빌드 19: 자동 음식 항목과 계산 흐름 복구

빌드 18은 제품명 확인과 입력칸 채우기만 제공했다. 이는 기존 자동 열량·용량·개수·소분 기능의 복구가 아니었다. 사용자의 실제 기대와 실패 안내를 확인해 이 부분을 수정했다.

- 사진에서 전체 열량과 용량이 읽히면 전체 영양성분표가 없어도 정상 FoodCandidate로 연결한다. 뉴케어 200ml/200kcal는 직접 입력으로 이동하지 않고 음식 목록 및 총 열량에 반영된다.
- ml는 ml로 유지한다. 200ml를 200g으로 저장하지 않는다. 개수 2개는 400kcal, 100ml 소분 1개는 100kcal, 100ml 소분 2개는 200kcal다.
- 탄수화물/단백질/지방/나트륨의 미확인 값은 저장할 때 null로 남긴다. 열량 계산을 다른 영양성분의 확인 여부로 막지 않는다.
- 열량이 안 보이면 현재 로그인한 사용자의 정확히 같은 제품명 기록만 찾아 이전 양·열량을 재사용한다. 화면에 이전 기록 기준임을 표시한다. 다른 맛/제품의 기록은 사용하지 않는다. 이전 g 기록을 현재 ml로 밀도 추정 환산하지 않는다.
- 기록 상태가 아직 로딩 중이거나 초기 빈 상태이면 본인의 기록 저장소를 직접 조회한다. 이 조회도 3초 안에서 끝내고 전체 사진 분석 대기 제한 안에 포함한다.
- 이전 정보도 없으면 미확인 정보를 만든 값으로 채우지 않고 기존 직접 입력/재촬영 선택지를 유지한다.

검증: 실제 Flutter Supabase 클라이언트(임시 QA 계정)로 사용자 제공 뉴케어 사진의 업로드·분석·결과 변환을 실행해 4.275초에 음식 항목 1개, 200ml, 200kcal를 확인했다. 2개 계산은 400kcal다. 이는 서버 스크립트만의 결과가 아니라 실제 앱 저장소와 공용 변환 코드의 결과다. 네이티브 카메라의 새 촬영 자체를 대신한 것은 아니다.

화면 테스트에서는 음식 목록 생성, 2개 선택, ml 소분 입력, 총 열량 및 저장 레코드까지 검증했다. 같은 크래커의 이전 기록 재사용은 별도의 테스트 기록으로 확인했으며 해당 테스트 수치를 실제 상품 영양정보로 사용하지 않았다. 사용자의 실제 기록이 존재/일치하는지는 사용자 계정의 읽기 결과에 달려 있다.


## 2026-10-14 제품 조회 설계 재검토

v19의 같은 이름 이전 기록 재사용은 철회하고 코드에서 제거했다. 제조사·규격·리뉴얼을 구별하지 못하므로 영양정보의 근거가 될 수 없다. 동일 이름의 과거 기록이 존재해도 사진의 미확인 용량·열량은 그대로 미확인이다.

실제 구현 감사 결과:
- 사진: Gemini 식별/사진에 표시된 영양정보 추출만 존재. 국내 공공데이터 조회 없음.
- 음식 검색: Gemini의 일반 음식 추정값. 공공데이터 검색 아님.
- 바코드: Open Food Facts 조회만 구현됨.
- 로컬 설정에는 국내 공공데이터 인증키가 없다. 운영 서버의 해당 인증키 존재 여부는 미확인이다.

필요한 제품 처리 흐름은 포장 식별 → 공공데이터 후보 조회 → 제조사/맛/규격/품목코드 대조 → 후보 확인 → 기준량에 따른 섭취량 계산이다. 이름만 일치하는 후보는 자동 확정하지 않는다. 현재 포장 표시와 DB 정보가 충돌하면 현재 사진 정보를 보존하고 차이를 안내한다. DB도 갱신 지연이 있어 최신 포장과의 대조가 필요하다. 데이터 없음/후보 불일치/조회 시간 초과/서비스 설정 누락은 각각 구분하고 직접 입력 전환을 유지한다.

공식 자료: https://www.data.go.kr/data/15100064/standard.do 및 https://various.foodsafetykorea.go.kr/nutrient/industry/openApi/info.do

공공데이터 연동은 아직 구현/실조회 완료 상태가 아니다. 이 변경의 검증 범위는 이전 기록 재사용 제거와 기존 사진 표시정보 처리의 회귀 테스트다.
