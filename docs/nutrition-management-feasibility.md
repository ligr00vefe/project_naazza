# 식습관·영양소 관리 구현 검토

확인일: 2026-10-20. 혈변 체크는 구현·서버 반영 완료. 아래 영양소 기능은 설계 검토이며 아직 앱에 추가한 기능이 아니다.

## 1. 결론과 현재 상태

식품을 정확히 고르고 먹은 양을 입력하면 공개 성분표를 이용한 영양소 섭취량 계산은 가능하다. 모든 상품의 모든 성분을 자동으로 알아내는 것은 불가능하다. 사진은 식품 후보를 찾는 수단이며, 원재료 이름 목록은 배합량이나 영양 분석 결과를 대신하지 않는다.

현재 서버 어댑터는 열량·탄수화물·단백질·지방·나트륨·당류·식이섬유·포화지방·트랜스지방·콜레스테롤·칼슘·철·칼륨·비타민 A/C/D를 정규화한다. 앱의 주 영양 모델은 기준량과 열량·탄수화물·단백질·지방·나트륨 중심이며, 추가 성분이 공공데이터 출처 정보에 있어도 일일 섭취량으로 집계하거나 목표 대비 그래프로 보여주는 기능은 없다. 인·B1·B2·니아신 등은 공급자 필드가 있지만 현재 정규화 대상에서 빠져 있다.

영양성분은 같은 응답에 여러 항목이 함께 오므로 칼슘·철·비타민을 더 표시한다고 항목마다 API를 추가 호출할 필요는 없다. 기록 저장·일/주/월 그래프는 저장된 섭취량을 계산하므로 외부 식품 API를 다시 호출하지 않는 구조로 만들 수 있다.

## 2. 가능한 것과 불가능한 것

| 기능 | 판정 | 필요한 조건 |
|---|---|---|
| 제품별 열량·단백질·칼슘·철 등 합계 | 가능 | 정확한 제품/규격과 성분 기준량, 실제 섭취량, 해당 성분 값 |
| 멸치볶음의 평균 영양 추정 | 가능 | 일치하는 표준 음식과 먹은 g 선택. 실제 조리법과 다르면 추정 표시 |
| 멸치+아몬드로 직접 만든 반찬 계산 | 가능 | 원재료 종류·가공 상태·재료별 g·먹은 비율. 기름·설탕·양념도 포함 |
| 원재료 목록만으로 정확한 함량 계산 | 불가 | 배합비·중량이 없으므로 정량 계산 불가능 |
| 필수 아미노산 9종 추적 | 조건부 가능 | 성분 데이터가 있는 식재료만. 별도 데이터 연결·단위 검증 필요 |
| 모든 국내 판매 제품의 모든 영양소 | 보장 불가 | 미수록 제품·신제품·규격 차이·누락 성분 존재 |
| 햇볕 20분으로 비타민 D 생성량/충족 판정 | 불가 | 시간만으로 개인의 생성량·상태를 결정할 수 없음 |
| 실외 활동 시간과 식이 비타민 D를 별도로 기록 | 가능 | 활동은 행동 기록, 식이는 성분표 기반 섭취량으로 분리 |

계산식: `섭취 영양소 = Σ(재료별 100g당 함량 × 사용 중량g / 100) × 먹은 비율`.
예를 들어 멸치 30g·아몬드 10g과 양념으로 만든 전체 반찬의 절반을 먹었다면, 전체 재료 영양소 합계의 0.5배다. 이 중량은 계산 방식을 설명하는 가정이다. 완성 음식의 영양값과 재료별 영양값을 동시에 더하면 중복 계산이 된다. 생것/건조/볶음 상태를 구분하고 조리 손실 자료가 없으면 추정치로 표시해야 한다. ml를 밀도 없이 g으로 바꾸지 않는다.

비어 있는 값은 0이 아니다. 예: 칼슘 값이 있는 음식이 8개 중 3개라면 ‘확인된 칼슘 합계 · 3/8개 정보 있음’으로 표시한다. 미기록 식사나 누락 성분을 영양 결핍으로 판정하지 않는다. 영양소 섭취량은 흡수량이나 질환 진단과도 다르다. 목표 대비 비율은 별도로 검증한 연령·성별 등 기준표를 적용해야 하며, 모든 사용자에게 하나의 기준을 강제하지 않는다.

비타민 D는 계절·시간·피부·노출 부위 등 영향을 받으므로 야외 20분을 생성 완료로 바꾸면 안 된다. [NIH 비타민 D 안내](https://ods.od.nih.gov/factsheets/vitaminD-healthProfessional/)

## 3. 실제 응답 확인

운영에 설정된 공공데이터 키로 아래 검색을 각각 1회씩, 총 3회 요청했다. 결과는 검색 명칭만으로 같은 제품이라고 확정할 수 없다는 점도 보여준다.

| 검색어 | 결과 수 | 확인된 첫 결과의 100g당 값 | 누락/주의 |
|---|---:|---|---|
| 멸치볶음 | 14 | 단백질 17.10g, 칼슘 766mg, 철 3.20mg | 비타민 D 공란. 다음 후보는 단백질 35g이지만 칼슘·철 공란 |
| 아몬드 | 15 | 첫 후보 단백질 17g | 첫 두 후보 모두 칼슘·철 공란. 원재료성 생아몬드로 확정할 수 없음 |
| 멸치 | 2 | 첫 후보 단백질 36.10g | 첫 후보 칼슘·철 공란, 두 번째는 칼슘 1200mg. 후보 확인 필요 |

멸치볶음 첫 후보 식품코드: `P114-300030000-1188`. 동일 검색어의 다른 후보를 섞어 빈 성분을 채우면 안 된다. 위 첫 후보와 동일한 음식을 20g 먹었다는 조건이라면 단백질 3.42g·칼슘 153.2mg·철 0.64mg으로 환산된다. 사용자가 먹은 반찬을 실제로 분석한 결과라는 의미는 아니다.

USDA 검색도 1회 실행했다. `Nuts, almonds`, FDC ID `170567`에서 단백질·칼슘·철뿐 아니라 라이신·류신·트립토판이 반환됐다. 아미노산 데이터 연결 자체는 기술적으로 가능하다. 국내 제품이나 한국산 건멸치와 동일한 식품이라는 증거는 아니므로 자동 대체하지 않는다. [해당 공식 데이터](https://api.nal.usda.gov/fdc/v1/food/170567?api_key=DEMO_KEY)

## 4. 사용할 데이터와 무료 호출 제한

### 현재 연결된 전국통합식품영양성분정보표준데이터

[공식 데이터·API](https://www.data.go.kr/data/15100064/standard.do). 일반 영양소·무기질·일부 비타민을 제공한다. 필수 아미노산 개별 항목은 이 표준 API에 없다. 개발계정 트래픽 표시는 10,000이며 운영계정 증설은 별도 신청이다. 공개 페이지에는 이 숫자의 일/월 단위가 명시되지 않아, 사용자의 승인 화면에서 ‘1일 트래픽 10,000’을 확인하기 전까지 아래 계산은 **하루 10,000회일 경우의 조건부 계산**이다. 키가 동작한다는 사실만으로 승인 한도를 알 수는 없다.

### 현재 연결된 식품안전나라 C002

[식품(첨가물)품목제조보고(원재료)](https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=C002). 원재료명·표시순서·품목제조번호·업소명·변경일 등을 제공하며, 재료별 g이나 전체 영양소를 제공하는 API가 아니다.

현재 공식 메시지에 명시된 제한:

- 06:00~19:00 인증키/서비스별 300회.
- 증분 파라미터 없는 조회는 시간당 100회.
- 파일 다운로드는 키/서비스별 하루 10회.
- 한 요청에서 최대 1,000건: 하루 호출 1,000회라는 뜻이 아니다.

30일의 주간 시간대 예산은 `300×30=9,000회`로 환산할 수 있다. 별도의 월 지급량이 아니고, 한 날의 남는 양을 다른 날로 넘길 수 없다. 야간을 포함한 전체 하루 한도는 이 안내만으로 확정하지 않는다. 사용자 조회에 임의의 최근 변경일 조건을 넣어 증분 제한을 회피하면 오래된 제품을 누락시키므로 그렇게 설계하지 않는다.

### 아미노산 후보 1: 국가표준식품성분DB

현재 공식 신청 링크는 [농촌진흥청 국립식량과학원_국가표준식품성분DB](https://www.data.go.kr/data/15143598/openapi.do)다. 이전 15107571 링크는 현재 404다. 코드 조회와 코드별 상세 성분 조회로 구성되며 아미노산을 포함한다. 무료·개발 트래픽 10,000으로 안내하지만 **현재 이용허락이 공공누리 제4유형(출처표시·상업적 이용금지·변경금지)**이다. 무료 API라고 앱의 모든 활용이 자동 허용되는 것은 아니다. 함량 환산·재배포와 향후 상업적 앱 이용 범위를 제공기관에 확인하기 전에는 정식 채택하지 않는다. 현재 앱에 미연결이며 해당 서비스 승인 여부도 확인되지 않았다.

### 아미노산 후보 2: USDA FoodData Central

[공식 API·이용조건](https://fdc.nal.usda.gov/api-guide/). CC0 공개 데이터이며, 일반 발급 키의 기본 제한은 IP당 시간당 1,000회다. 검색과 상세 API가 있다. 운영용 키는 별도 발급해야 한다. DEMO_KEY는 시간당 30회·하루 50회라 운영에 쓰면 안 된다.

일반 키는 24시간 균등 사용 시 하루 24,000회, 30일 720,000회로 산술 환산된다. 이것은 월 사용권이 아니라 시간당 제한의 환산이다. 집중 시간대에 몰리면 월 합계가 작아도 실패할 수 있다. 호출 서버 IP 공유 여부와 실제 응답 한도 헤더를 확인해야 한다. 한국 식품과 미국 표준 식품의 품종·건조·염장·조리 상태 차이를 사용자 확인 없이 동일시하지 않는다.

## 5. 호출량 계산: 현행과 확장 단계

아래는 실측 사용량이 아닌 용량 계획이다. 실제 일간 사용자 수·조회 행동 통계가 없으므로 ‘현재 몇 %를 쓰고 있다’고 단정하지 않는다. 모든 수치는 공급자별로 계산하며 서로 다른 API의 한도를 합산하지 않는다.

공통 가정: 매일 사용하는 사용자 N명, 1명당 하루 3끼×3개=9개 음식 조회. C002 원재료 버튼은 서로 다른 제품 3개/명/일. 모든 원재료 조회가 06~19시에 발생한다고 보수적으로 가정한다. 아래 표에는 추가 페이지·사용자의 재시도는 포함하지 않았으므로 별도 여유가 필요하다.

현행 코드상 영양 검색은 이름 변형을 최대 7개까지 순차 요청하고, 첫 유효 결과에서 종료한다. 전체 검색 예산은 5.5초이므로 모든 검색이 항상 7회를 사용하는 것은 아니다. 그래도 부하 계산의 상한에는 7회를 사용한다. 원재료는 버튼을 눌렀을 때만 요청하며, 같은 사용자·품목제조번호·날짜의 재요청은 로컬 캐시를 쓴다. 캐시 보존은 7일이고 다음 날짜에는 새로 조회한다. 사용자 간 공유 캐시는 현재 없다.

### A. 현재 영양 조회와 1단계 영양소 합계

`하루 호출 = N×9×이름 검색 시도 수`. 1단계는 같은 응답에 있는 성분을 저장·집계하므로 **성분 추가에 따른 외부 API 추가 호출 0회**다. 다만 검색을 다시 누르는 행위나 다음 페이지는 추가 요청이다.

| 일간 사용자 | 1회에 검색 성공: 일/30일 호출 | 하루 10,000회 조건부 사용률 | 7회 검색 상한: 일/30일 호출 | 조건부 사용률 |
|---:|---:|---:|---:|---:|
| 1 | 9 / 270 | 0.09% | 63 / 1,890 | 0.63% |
| 10 | 90 / 2,700 | 0.9% | 630 / 18,900 | 6.3% |
| 100 | 900 / 27,000 | 9% | 6,300 / 189,000 | 63% |
| 1,000 | 9,000 / 270,000 | 90% | 63,000 / 1,890,000 | 630% |

30일 비교 분모는 조건부 `10,000×30=300,000회`. 일일 한도가 확정되면 일률적인 매일 사용 가정에서 월 환산 비율도 동일하다. 운영 목표를 한도의 50% 이하로 잡으면 영양 검색은 1회 성공 기준 최대 555명, 7회 기준 79명이다. 이 50%는 개발상 여유 목표이며 제공기관의 안정성 보장이 아니다.

### B. 원재료 버튼 조회

`주간 시간대 일 호출=N×3`. 앱의 같은 날 중복 조회 캐시는 이미 반영된 ‘서로 다른 제품’ 가정이다. 사용자 간 재사용은 반영하지 않았다.

| 일간 사용자 | 주간 시간대 일/30일 호출 | 300회/일 대비 사용률 |
|---:|---:|---:|
| 1 | 3 / 90 | 1% |
| 10 | 30 / 900 | 10% |
| 100 | 300 / 9,000 | 100% |
| 1,000 | 3,000 / 90,000 | 1,000% |

50% 예산은 주간 시간대 하루 150회·시간당 50회다. 제품 3개씩 조회하는 경우 일간 사용자 50명이 일 예산의 경계다. 단, 50명이 한 시간에 모두 누르면 150회여서 시간당 100회 제한을 넘는다. 10명이 3개씩 같은 시간에 요청하면 30회로 시간 한도의 30%, 주간 일 한도의 10%다. 페이지를 더 읽거나 실패 후 재시도가 있으면 이 수치도 증가한다. 원재료 조회에 큐·호출 계수·중복 합치기·상태 안내가 필요하고, 식사 기록 자체를 막아서는 안 된다.

### C. 재료별 계산·아미노산 확장

보수적 설계 가정: 1명당 하루 요리 3개×재료 4개=12개 재료. 재료마다 검색 1회+상세 1회, 처음 조회 시 24회/명/일. A의 ‘9개 음식’ 시나리오와 대체 관계로 제시하며, 동시에 모두 사용하면 두 호출량을 더해야 한다. 동일 식품 코드·출처 버전·가공 상태로 확인된 성분표를 활용하면 재조회 수를 줄일 수 있지만 현재 구현된 캐시는 아니다.

| 일간 사용자 | 매번 검색+상세: 일/30일 | 성분표 재사용 90%를 달성했을 때: 일/30일 |
|---:|---:|---:|
| 1 | 24 / 720 | 2.4 / 72 |
| 10 | 240 / 7,200 | 24 / 720 |
| 100 | 2,400 / 72,000 | 240 / 7,200 |
| 1,000 | 24,000 / 720,000 | 2,400 / 72,000 |

소수 호출 수는 여러 날 평균이다. 90%는 달성 목표 예시이며 실측 적중률이 아니다. RDA를 이용할 경우 하루 10,000회 승인 조건에서 100명은 캐시 없이 24%, 90% 재사용 시 2.4%다. 다만 이용허락 확인 전에는 출시 가능 판정을 내리지 않는다.

USDA 일반 키로 100명이 24회씩 쓰면 하루 2,400회·30일 72,000회로 24시간 환산 용량의 10%지만, 전부 한 시간에 몰리면 시간 한도의 240%다. **하루 합계만으로 안정권이라고 하면 잘못이다.** 90% 재사용 시 평균 240회/일이지만 최초 사용일에는 2,400회일 수 있다. 50% 목표는 시간당 500회이며 하루 12,000회·30일 360,000회는 균등 분산했을 때의 환산이다. 무료 데이터 파일을 앱에 필요한 범위로 미리 구성하는 방식도 API 호출을 줄이는 후보지만, 버전 갱신·배포 크기·라이선스 확인이 선행되어야 한다.

### 초기 운영 판단

- 위 가정의 10명 테스트: 영양 조회는 조건부 0.9~6.3%, 원재료는 주간 일 한도 10%다. 10명이 세 제품을 한 시간에 모두 조회해도 시간 한도 30%다. 식품 API 관점에서는 50% 목표 안의 시험 규모다.
- 100명 실사용: 영양 조회 최악 63%, 원재료 주간 한도 100%다. 현행 구조를 무료 API 안정권으로 승인할 수 없다.
- 1,000명 실사용: 현행 원재료 조회와 영양 검색 상한 모두 기본 예산을 초과한다. 데이터 배포 방식·정확한 코드 재사용·운영계정 증설을 검토해야 한다.
- 무료 호출 제한은 전체 서버가 공유한다. 사용자마다 키 한도가 따로 생기지 않는다.
- 과거 같은 이름의 식사에서 영양값을 재사용하지 않는다. 코드·출처 버전·규격 확인을 거친 공개 성분표 활용과 과거 기록 이름 복사는 다르다. 제품 리뉴얼·규격 변경 시 새 확인이 필요하다.
- 원재료 원문은 사용자가 요청한 기존 방침대로 음식 DB에 누적 저장하지 않고 버튼 조회와 로컬 캐시를 유지한다. 서버 원재료 DB를 새로 쌓는 방식은 이번 계획에 포함하지 않는다.

사진 AI 요청은 이 계산과 별도다. 사진 3장/명/일이면 Gemini 요청도 최소 3N회이고 재시도는 추가된다. 실제 모델·프로젝트별 무료 RPM/TPM/RPD 승인값을 확인하지 않았으므로 AI까지 포함한 전체 서비스의 무료 안정권 %는 확정할 수 없다. Supabase 저장·전송·Edge Function 사용량도 식품 API 한도와 별개다. ‘식품 API 무료’가 ‘앱 전체 무제한 무료’를 의미하지 않는다.

## 6. 우선순위와 완료 기준

1. **완료: 혈변 체크.** 입력·수정·DB 저장·상세·간단 요약 반영. 이전 기록은 미기록 유지.
2. **우선: 현재 연결된 영양값을 끝까지 전달.** 성분별 단위·기준량·섭취량·출처·자료 날짜·누락 여부 보존. 칼슘·철·식이섬유·당류·나트륨·비타민 D부터 일/주/월 합계 제공. 한 건의 원본 응답과 앱 합계를 대조하는 테스트가 완료 기준.
3. **동시에: 호출량 계측.** 공급자별 일/시간 호출, 이름 변형·페이지·수동 재시도, 오류 사유, 캐시 적중률을 개인정보·인증키 없이 집계. 7일 실제 측정 후 예산 재계산. 승인 화면의 실제 1일 트래픽도 확인. 계측 전 수치는 용량 계획으로만 사용.
4. **다음: 재료별 레시피.** 재료 선택·가공 상태·g·전체 조리량·먹은 양 입력, 양념 포함. 완성 음식 계산과 재료 계산 중 하나를 선택. 표준 레시피는 수정 가능하고 추정 표시.
5. **그다음: 아미노산.** RDA 이용허락 확인 또는 USDA 키·한국 식품 대응표 검증 후 연결. 필요한 9종이 없는 음식은 정보 없음. 데이터 없는 항목을 AI로 채우지 않음.
6. **보류: 운동·햇빛 생활관리.** 현재 식습관·영양소 작업에 집중. 이후 야외 활동과 식이 비타민 D를 독립 항목으로 추가 가능.

이번에 영양소 관리 전체를 구현했다고 보고하지 않는다. 구현 가능한 기본 합계, 추가 데이터·재료량이 필요한 확장, 계산하면 안 되는 건강 판정을 구분한 계획이다.
